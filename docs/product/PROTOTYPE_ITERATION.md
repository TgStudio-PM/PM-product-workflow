# 原型需求迭代与接续

本指南面向产品经理与 Coding Agent 在使用者项目中开发和持续迭代桌面 Web 原型，开发者可协作实现。已有原型优先复用其技术栈、设计约束、组件与代码结构；也可从明确需求建立初版原型。每轮聚焦一项需求变化，不交付通用应用脚手架，也不要求重写全部项目文档。

## 一轮工作的主链

需要对页面原型做只读评审并按修正版本复核时，可按需使用 [gov-enterprise-cn 评审 Profile](../../profiles/gov-enterprise-cn/PROFILE.md) 及其[评审模板](../../profiles/gov-enterprise-cn/REVIEW_TEMPLATE.md)；这补充评审与复核记录，不替代本指南的业务路径验收。

| 阶段 | 输入 | 动作 | 最低输出 |
| --- | --- | --- | --- |
| 1. 明确需求 | 变化、来源或确认责任人、目标用户和目标 | 说明要改变什么、为何改变、期望结果。关键缺口请负责人确认。 | 目标、范围、待确认项 |
| 2. 查影响 | 当前原型、相关事实、页面和共享实现 | 查受影响页面及非导航入口、角色、字段、状态、数据与共享组件；列出跨页影响和依据。 | 影响清单与冲突 |
| 3. 开发/迭代原型 | 已确认目标、影响清单、项目现有代码 | 沿用现有技术栈、设计约束与组件，完成最小完整且可评审的代码改动。未确认的关键业务决策不得自行补造。 | 原型代码成果、未完成项 |
| 4. 业务路径验收 | 目标角色、相关场景和当前版本 | 产品负责人检查受影响入口、字段、状态变化、异常及回退，记录实际结果。仅在交付要求离线运行时检查目标环境入口。 | 业务验收记录与未决项 |
| 5. 同步事实 | 需求来源、原型表现、实现及验收证据 | 更新受影响的既有事实和版本差异，说明来源；小改动采用简短记录。 | 可追溯变化、下一步 |
| 6. 接续与反馈 | 当前基线、变化记录和交付需要 | 按实际接收者准备接续或交付；新会话需续作时先核对实际现场并保留未提交改动，再依据记录接续，不重复已完成任务或已否定方案。收到开发反馈后核对版本并决定是否继续迭代。 | 接收方、材料、反馈或待办 |

例如，某字段规则变化同时影响新建表单、详情展示和旧草稿：先确认规则与已有草稿处理要求，再检查三处实现和共享组件，改代码并分别核对新录入与旧草稿；将确认来源、版本差异和未决迁移问题记入现有模块记录，交接时说明尚待开发确认的行为。该例说明检查范围，不定义任何具体业务字段或规则。

## 事实与差异

在已有模块 `CURRENT.md`、规则、流程、决策或对接记录中按需更新，不为每轮机械创建文件。区分需求来源、原型可见行为、已核对实现和版本；差异写明来源、版本/日期、现状及待确认责任人。未知内容保持待确认，不从代码反推需求，也不猜接口、权限或持久化方式。

小改动记录变化、证据和验收；跨角色、状态或流程变化时，再同步实际受影响的规则、流程、页面索引和交接引用。规则变化时先确认旧草稿和旧终态的处理；未确认前不得静默截断、清空或重置已有内容。保持事实只有一个权威正文，其它位置链接或短述即可。

## 从原型走到开发实现，再接收反馈

当需求已进入开发代码，沿用同一项需求和已有记录，不另建一套生命周期台账：

| 环节 | 本轮要核对什么 | 记录到哪里 |
| --- | --- | --- |
| 需求变化 | 当前有效决定、角色与状态、旧数据处理；被替代的旧说法退出当前规则 | 既有需求/决策正文 |
| 原型与开发对照 | 按同一需求查原型入口和实际开发分支/提交，区分已实现、遗漏、差异与待确认 | 已有需求文档或对接记录 |
| 影响与回归 | 标题/导航/直达入口；列表/筛选/排序/分页/导出；详情/消息/角色范围；按实际影响选用 | 本轮任务和验收记录 |
| 评审处置 | 对照确认需求和版本复现。区分实现缺陷、需求取舍、环境问题和证据不足；不按评审数量机械修复 | 对应发现项及处置依据 |
| 交付与回流 | 对照开发提交、实际交付包和接收方运行版本。说明本轮改动是否已经进入所发版本，再处理反馈 | 现有交接或反馈记录 |

原型并不总与后续开发同步。开发者直接调整后，先核对调整依据；已确认的变化同步到原型和权威事实，未确认差异保留待确认，不自动把代码当新需求。反馈没有版本或复现条件时，先补齐定位所需信息，不因旧包未更新而反复修改已经修好的代码。

按接收方选择材料：产品评审关注入口和业务路径，前端协作关注页面/组件及变化，后端协作关注字段、状态和已确认契约。只有确需交付文件时才打包；日常修改不触发新包或发布。包发出后保持该版本不变，后续修正形成新候选。正式应用涉及迁移、配置或依赖变化时，引用开发团队的升级与回退说明，不从原型工程验证推断目标环境已验收。

## Coding Agent 提示词

```text
请在我的原型项目中围绕本轮需求完成一次开发/迭代。
项目与模块：<项目名>/<目标模块>
项目入口、当前版本和相关路径：<实际路径；未知写待确认>
需求、来源及确认责任人：<本轮信息>
目标、范围和禁止事项：<本轮信息>
沿用现有技术栈、设计约束、组件和目录。先核对实际现场和未提交改动，再列出受影响页面/入口、角色、字段、状态、数据和共享组件，以及待确认冲突；明确的需求可实施，关键缺口先请我确认。完成代码改动后，说明我应如何按业务路径验收。收尾最小同步相关事实、版本差异、未决项和接续/交付需要。不要重复已完成任务或已否定方案，不猜业务规则、接口或生产行为。
```

需要向前端、后端或 QA 交付本轮需求时，可按需调用 `gov-requirements-doc-writer` 整理或更新文档；它不替代本指南中的原型实现和业务路径验收，也不要求每轮生成 PRD。

只读界面走查使用 `gov-ui-reviewer`；落实明确的界面调整使用 `gov-ui-refactor`。两者共用现有 Profile，按任务选择，不要求先评审再实施。

将确定性改动交给开发者或执行型 Coding Agent 时，可按需引用[可选执行任务包模板](../../templates/optional/AGENT_TASK.md)，写明项目路径基准、实际基线、最小证据、文件边界和验证方式。需求判断、范围协调与最终产品验收仍由主线负责人负责；模板不是必填流程。

## 四项工作流验收口径

1. 是否围绕明确需求分析影响，并完成可评审的原型代码改动？
2. 是否根据来源同步需求、原型表现、实现说明和差异？
3. 需要续作时，是否用新会话核对实际现场、保留未提交改动，并依据记录接续而不重复已完成任务或已否定方案？
4. 是否向实际接收方提供所需材料，并如实记录验证范围？若交付需要离线预览，须在目标环境检查入口与核心路径并独立验包；这不是每轮统一门槛。

AI 静态判断不能代替产品负责人验收。代码检查、构建、HTTP、离线运行与目标项目业务验收分开记录；未执行或待确认的项目据实标注。
