# 原型需求迭代与接续

本指南用于产品经理与 Coding Agent 在既有桌面 Web 原型上持续迭代和交接。每轮围绕一项需求变化推进，不要求每次重写全部项目文档。开始前确认自己有权使用所提供的项目资料；授权私有资料只留在自己的工作区，不要上传到本仓库。

## 一轮工作的主链

| 阶段 | 输入 | 动作 | 最低输出 |
| --- | --- | --- | --- |
| 1. 说明变化 | 需求变化、提出者或确认责任人、目标用户和目标 | 明确要改变什么、为何改变、期望何时可评审。需求足够明确可直接执行；关键缺口或冲突列出并请负责人确认。 | 一句目标、范围、待确认项；简单变更可直接记在本轮短记录中。 |
| 2. 查影响 | 相关事实文件、当前基线和原型入口 | 检查受影响页面、导航及非导航入口、角色、字段、状态、数据和共享组件；寻找跨页面或前后端影响。导航不是需求全集。 | 影响清单及依据；不确定项与确认责任人。 |
| 3. 更新原型 | 已确认目标、影响清单、现有框架 | 在现有原型和共享模式上做最小完整改动。不得自行填补关键业务缺口；无法确认时暂停该决策并保留可评审问题。 | 可评审原型改动；明确未实现或待确认项。 |
| 4. 验收路径 | 目标角色、业务场景、原型基线 | 由产品负责人按受影响业务路径检查入口、角色、字段、状态变化、异常和回退。记录实际看到的结果；需要离线交付时在目标环境打开。 | 产品验收结论、环境和未通过项；未检查写“未执行”或“受阻”。 |
| 5. 同步事实 | 需求确认、原型观察、已核对实现及验收证据 | 更新相关项目或模块事实，记录版本与来源；把差异并列写出，不把实现自动升级为需求。小改动用短记录；跨角色或状态变更补足相关规则、流程和决策。 | 可追溯的变化、证据、差异、待确认和下一步。 |
| 6. 交接与回流 | 当前基线、变更记录、验收及差异 | 按接收方选择短接续、评审说明、实现说明或交付包；本轮需要交接或新会话续作时，用一个实际新会话读取交接材料并尝试下一步，核对是否能接续且不重复已否定方案。开发反馈回来后核对其针对的需求与版本，更新事实并决定是否需新一轮迭代；尚未收到反馈时保持待确认。 | 接收方、版本/入口、完成项、验证层次、风险和下一步；新会话实测结果及开发反馈状态。 |

## 把事实与差异放在一起

在已有模块 `CURRENT.md`、相关决策记录或 `contracts/` 对接记录中，按现有结构记录这次变化；不要为每轮强制创建新文件。对服务端字段、接口或行为的讨论可使用已有的 API 对接记录。未共同确认的内容仍标为待确认。

开发实现或反馈回流时，按需使用[可选 API 对接记录](../../templates/optional/API_HANDOFF.md)，分别记录原型、实现与反馈版本；无需每轮新建表。

| 事实类别 | 可以证明什么 | 不能据此推断什么 |
| --- | --- | --- |
| 已确认需求 / 规则 | 有来源和确认责任人的产品要求 | 未核对的页面表现或后端实际行为 |
| 原型表现 | 指定版本原型中实际可见、可操作的内容 | 需求已批准、数据已持久化或生产可用 |
| 已核对实现说明 | 指定版本代码或运行环境的实现情况 | 未经确认的产品意图或其他版本的行为 |

记录差异时写清“类别 / 证据来源 / 版本或日期 / 现状 / 差异 / 待确认负责人”。版本或来源未知时标为“待确认”；不要从代码反推确认需求，也不要用旧版验证覆盖新版结论。

- **小改动**（文案、单字段呈现或局部交互，未改变角色、状态或跨页规则）：在现有 `CURRENT.md` 追加简短变化、证据、验收结果和下一步；相关规则没变时不重复抄写。
- **跨角色或状态变更**：同时核对相关 `BUSINESS_RULES.md`、`PAGE_FLOW.md`、`DECISIONS.md`；更新受影响规则、角色、状态、例外和确认来源。只更新实际受影响文件，并让 `CURRENT.md` 链接权威记录。
- **与实现或接口存在差异**：分别写需求、原型和实现证据；在既有 `contracts/` 记录中保留待确认字段/行为、确认责任人和验证状态。不要猜接口地址、方法、权限或持久化方式。

## 规则变化时核对旧记录

字段长度、必填、枚举或终态条件变化时，影响面也可能包含已保存草稿、历史记录、只读详情及恢复入口。先确认旧值应如何保留、提示、修正或迁移；不要为了满足新校验静默截断、清空或重置已有内容。

按受影响范围对照新录入、旧草稿、旧终态和边界值检查，并记录实际版本与结果。只改页面提示或新建路径，不能证明已有记录符合新规则；未确认的服务端处理仍放在对接待确认项中。把检查结果记入本轮已有验收记录，不另建一套台账。

## Coding Agent 启动提示词

替换尖括号内容并只提供本轮相关文件路径。不要粘贴无权公开的私有项目资料。

```text
请在既有桌面 Web 原型中完成一项需求迭代。
目标与变更原因：<内容>
需求来源/确认责任人：<来源；未知写“待确认”>
当前版本、分支或入口：<可核对基线；未知写“待确认”>
本轮范围与禁止事项：<内容>
请先读取：<项目事实路径、相关模块事实路径、原型路径>
先列出受影响页面/入口、角色、字段、状态、数据、共享组件及待确认冲突；明确需求可直接实施，关键缺口先列给我确认。然后在现有框架中完成可评审改动，说明产品路径应如何核对。不要从代码推断已确认需求，不猜接口或生产行为。收尾分别报告需求迭代结果、事实及差异记录、新会话接续验证、按接收方交付的结果；未执行的项目明确说明。区分已确认、待确认、原型观察和实现证据，更新受影响的既有记录。
```

## 四项工作流验收口径

每次完整主任务都应据实回答以下问题；没有证据的项目写“未执行”或“受阻”，不要用 AI 静态判断代替人或浏览器实际检查。

1. 是否输入明确需求并评估影响，在桌面原型完成可评审迭代？
2. 是否建立按证据记录的项目事实，区分已确认需求、原型表现、实现说明与差异？
3. 是否实际开启新会话并依现有记录接续，且避免重复已否定方案？
4. 是否按接收方交付可用材料？v0.1 至少保留已实测离线预览交付物和独立验包要求；具体任务按需选择交付类型，不要求每轮制作三类包。

新指南或提示词的存在不是用户验收。独立非开发产品经理完成完整主任务的试用仍待进行；浏览器、AI-only 或工程演练不能替代该试用。机器检查不替代业务验收。需要声称支持 `file://` 离线时，必须在目标浏览器和交付物上实测入口与核心路径；静态结构、构建或 HTTP 结果不能代替。
