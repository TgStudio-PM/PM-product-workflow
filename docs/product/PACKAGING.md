# 按需准备原型交付包

先确认接收方和用途，再决定是否需要 ZIP。使用者项目的文件范围必须以实际需求、原型入口、已确认页面和交付约定为依据。三类配置仅是可定制起点，不是可以直接套用的公共白名单。

## 选择交付类型

| 类型 | 适用目的 | 配置起点 | 需要确认的内容 |
| --- | --- | --- | --- |
| 静态预览 | 接收方需要查看可离线运行的页面 | `templates/package-profiles/static-preview.json` | 实际入口、页面、相对资源、许可文件及必须包含的页面内容 |
| 前端源码 | 接收方需要继续检查或修改前端代码 | `templates/package-profiles/frontend-source.json` | 实际源码根目录、必要配置/资源、构建说明及许可文件 |
| 后端需求材料 | 接收方需要评审产品事实和待确认契约 | `templates/package-profiles/backend-requirements.json` | 已确认的需求、规则和流程记录；真实接口或权限未知时标待确认 |

## 复制并按证据定制

如接收方需要需求说明，可先按需使用 [`gov-requirements-doc-writer`](../../.agents/skills/gov-requirements-doc-writer/SKILL.md) 准备或更新已有需求材料，再依据实际交付范围选择文件。该文档方法不新增打包必需文件、字段或 CLI。

先把相应 JSON 复制到使用者自己的项目，再根据当前源码、需求、接收方约定逐项调整 `include`、`required`、输出路径，以及所选配置实际支持的 `entry` 字段；`pages` 仅在使用的静态预览配置中适用。实际字段以打包器支持的配置为准。`path/to/...` 是待替换的占位路径；只要仍有未替换占位符，就不能当作完成配置或运行打包。

检查白名单不会替代授权和范围判断。只列本次接收方确需的文件，并确认相对引用、许可声明与必要依赖均已包含。按实际来源保留应随文件提供的许可和第三方声明；不能把本项目模板的许可视为使用者新增内容的许可。不要将私有或真实项目资料复制到本公开仓库。

## 减少重复工作

- 复用并核对项目已有的 Profile 和已验证封包入口；本轮只查看白名单、相关变更及命中的错误记录，不重新扫描整个工程或历史归档。
- 先区分配置、源内容、构建、包结构或打开方式的问题，再修正对应环节。同一输入失败后不要原样重跑；不要为匹配检查文案而改变已确认需求。项目工具已有封包前预检时直接使用，不额外串行重复同一预检。
- `PROFILE-09` 会列出未被 `include` 覆盖的相对路径；逐文件重复或保留名的 `SOURCE-03` 会指出归档相对路径及原因。按诊断核对原有白名单并修正 `include`，不要删除真实文件或放宽 `required` 来绕过检查。`SOURCE-05` 会列出缺失的 Profile 相对路径，最多显示 20 项；超出时按省略数量继续核对 Profile。
- 封包先检查声明的必需文件、入口和页面是否被白名单覆盖且实际存在，齐全后再沿用原有流程收集内容；缺文件时不白读已有载荷。普通打包自动执行，无需另加预检命令。若同时存在缺失路径和文件不可读，先处理路径诊断，再核对内容读取问题。
- 已有候选仅需验包时直接运行 `--verify`，不重新生成 ZIP。运行检查仍按交付类型完成；长日志留在自己的验证目录，对话只回传结果、问题位置、包路径和 SHA256。只对本轮实际核验的候选及范围作结论。

## 构建与独立验包

从可访问该脚本的 PM-product-workflow 工作副本运行。为每次新候选使用尚未存在的输出文件名；脚本拒绝覆盖已有 ZIP。验证已有包时只运行 `--verify`，不要通过重建覆盖原件。

```text
python "<PM-product-workflow 根目录>/.agents/skills/pm-prototype-packager/scripts/package.py" --source "<项目根目录>/<实际源码根目录>" --profile "<项目根目录>/<已定制Profile.json>" --output "<项目外输出目录>/<唯一文件名.zip>"
python "<PM-product-workflow 根目录>/.agents/skills/pm-prototype-packager/scripts/package.py" --verify "<项目外输出目录>/<唯一文件名.zip>"
```

完成后核对 ZIP 清单、manifest、哈希和独立验包结果。它们说明包结构及配置范围，不证明业务正确或目标环境运行通过。若交付确实要求离线预览，再在接收方目标环境打开声明的 `file://` 入口并检查核心业务路径；其他场景不把离线包或浏览器检查设为统一门槛。
